# 项目价值与简历写法

## 推荐定位

**vLLM 推理服务准入控制与可复现 SLO 评测平台**  
Python / AsyncIO / FastAPI / vLLM / Kubernetes

适合 AI Infra、推理服务、模型部署、性能评测和后端基础设施岗位。价值集中在服务治理、异步资源正确性和实验诊断。当前成果不足以支撑“自研调度算法优于原生 vLLM”“CUDA 内核优化”“多机多卡高可用”等表述。

## 可直接放进简历

- 基于 vLLM 构建异步流式准入网关，实现并发与工作量双预算、有界队列、等待补偿、断连取消监督及幂等资源回收；通过 23 项功能测试，并完成真实 GPU 取消与后续请求恢复验证。
- 搭建固定轨迹开放环评测流程，在 Kubernetes 单 RTX 5090 环境完成 36 组同设备配对实验与 4 组新轨迹验证，累计 11,560 次请求；保留失败分母，核验 token、发送落后、终态和运行来源。
- 对比原生 FCFS、开发选择的容量配置与同预算网关，结合引擎运行并发及外部队列定位性能退化，识别静态完整请求成本预算与连续批处理之间的冲突，交付可复算数据和图表。

空间有限时使用前两条；第三条适合强调性能诊断能力。23 项是 CPU/模拟后端及本地 HTTP 功能测试，40 组才是真实 GPU 性能运行。

## 一分钟讲述

我实现了放在 vLLM 前面的流式准入网关，用并发与估计工作量限制过载，并处理排队、断连和资源回收。随后设计了固定到达轨迹的开放环测试，用原生 FCFS、开发集选择的容量配置和同预算网关作对照，完成 40 组单卡运行。结果显示低负载延迟拟合很准，却没有带来更好 SLO：近容量时完整请求成本预算让引擎同时运行请求减少，外部队列积累。最终建议保留原生 FCFS，并交付全量请求记录与复算脚本。这让我能具体讨论服务生命周期、连续批处理和性能实验的边界。

## 追问要点

1. **有没有提速？** 本轮没有证据支持优于原生引擎；近容量 P/B0 配对相对变化中位数 −68.12%。验证 P/B2 +38.24% 只有一个种子，且 P/B0 仍为 −58.22%。
2. **拟合误差只有 0.55%，为什么不好用？** 拟合的是低负载单请求延迟，不是可相加的并发资源消耗；共享批处理改变了服务过程。
3. **因果是否证明？** 监控与预算降低批处理机会的解释相容，但尚未消融预算、排空保护与代理开销。
4. **取消怎么证明？** 关闭前同时观测引擎 running 与正预算，关闭后观察预算清零、引擎空闲及后续请求成功。约 58 ms/0.62 s 是隔离观测，不是 SLA。
5. **可重复性是什么级别？** 公开数据可离线复算；重跑 GPU 需匹配环境并重新标定。公开配置经过脱敏，不能冒充原始冻结字节。
6. **是否多卡？** 本轮 TP=1、同一张卡顺序运行，不能写成八卡或分布式实验。
